# The first real loop: what it sent, 2026-10-12

Two DGT boards chained on one serial line (COM5, a USB serial adapter,
9600 8N1): the board of `docs/real-board-2026-10-12.md` - serial **06310**,
firmware **1.9**, serial cable - and a newer one, USB-C to serial, firmware
**4.0**, which answers on the loop as **12799**. They work together in DGT
LiveChess, so the cable is sound. No clock was attached to either, and
nobody was at the boards: whatever stood there is what was read.

Until this session every byte of `lib/alnasl/dgt/bus.ex` was marked
ASSUMED. This is what was sent, what came back, and what it settles. The
tool is `mix alnasl.loop` (`--probe` sends a script of commands and writes
down every byte; `--discover` and `--watch` do what the box does). Every
recording is a test fixture, whole:
`test/fixtures/captures/real-loop-*.jsonl`, read by
`test/alnasl/real_loop_test.exs`.

## The two boards

| | 06310 | the newer one |
|---|---|---|
| Cable | serial | USB-C to serial |
| Answers on the loop as | 6310 (`31 26`) | 12799 (`63 7F`) |
| Firmware (`8B`) | 1.9 | 4.0 |
| Serial number | 06310 - its address | **not read**. Ends in 730; `40730` is the likeliest reading of three collisions. Not derived from 12799 in any way that could be found |
| First bus command after a single-board command or "end bus mode" | **swallowed**; the next is answered | answered |
| Its memory | events only; some with bit 4 set (`5x` for `4x`) | events with one to four bytes below 0x40 between them (time stamps, presumably) |
| First answer to "what changed?" | everything since it was switched on (290 bytes) | everything since its last start-of-game mark (1319 bytes) |
| In a collision | loses | wins: its bytes come through nearly whole |
| Piece codes | the published ones | the same (a white and a black knight were on it: 0x03, 0x09) |
| Clock | none attached; `10 00 00 01 32 12 28` | none attached; `00 00 00 00 00 00 20` |

06310's clock answer is worth a second look. Status 0x28 has the "no clock"
bit, and bytes 3-5 are `01 32 12`: the last time its memory holds for that
side is `71 32 12`, written when a clock was last on it. The board keeps
the dead clock's last time and says "no clock" beside it, exactly as it did
on its own cable. So the layout of the times is very likely the
single-board one - but no running clock was seen, and it stays ASSUMED.

## Bus mode is not what it was taken for

The assumption was a switch: in single-board mode a board ignores the bus,
in bus mode it ignores everything else. Neither half is true.

- **Both boards answer bus commands in any mode.** After "end bus mode" to
  everybody (05), a ping to everybody is answered by both.
- **Both boards answer single-board commands in any mode**, bus mode
  included - both at once. That is the whole of what the owner saw when
  COM5 was added as one board: `data/captures/board-4/20261012-150011.jsonl`
  has a board dump requested every three seconds and two dumps arriving on
  top of each other every time.
- What the mode does change was seen on 06310 only: once it has been spoken
  to as a single board - any single-board command, or "end bus mode" - **the
  first bus command it hears is swallowed**. It switches the board over and
  is not answered; the next one is. (DGT's text says as much: a board in
  single-board mode that meets a bus command "switches to bus mode" without
  processing it.) The newer board answers the first.
- The bus-mode byte itself needs a moment. A command written in the same
  breath was lost three times in ten (09); after 30 ms, never in 48 (10).

For the driver: the bus-mode byte when the port is opened, 50 ms, and a
question that goes unanswered is simply asked again. And **never a
single-board command on a line that may be a loop** - see below for what
one did.

## Finding the boards

`Alnasl.Dgt.Loop`, as recording 13 has it:

```
tx 4A                          the bus-mode byte, 50 ms
tx 87 00 00 07                 ping, everybody
rx 87 00 06 63 7F 6F           12799, after 607 ms
rx 87 00 06 31 26 64           06310, after 734 ms       ... listened to for 1100 ms
tx 8A 63 7F 6C   rx 87 ...     12799: sit out the next one
tx 8A 31 26 61   rx 87 ...     06310: sit out the next one
tx 87 00 00 07                 ping: nobody new, 1100 ms
tx 8A ... 8A ... 87 00 00 07   once more: nobody new
```

Two rounds without anybody new and without garbage end it, and each
address heard is then pinged once by name (two answers on top of each
other can make an address nobody has): 3.5 seconds for two boards, 2.3 for
one. The waits the boards chose in 20 pings were 26 to
1020 ms, so 1100 ms is listened; a round in which something arrived that
was no whole answer counts as "somebody is there", and is asked again.
With twelve boards most first rounds will have a collision; that is what
the sitting out is for.

## A board's memory

"What changed?" (0x83) and "from start" (0x86) carry the same thing: what
DGT calls the EEPROM format, the board's own record of events.

| Bytes | Meaning | How it is known |
|---|---|---|
| `40`-`5F`, then a square | that square now holds the piece in the low nibble (0: empty); squares as in a dump, a8 = 0 | the events since "switched on", applied to an empty board, give the position of the dump - both boards (`real_loop_test.exs`) |
| `60`-`69`, minutes, seconds | a clock time, hours in the low nibble, BCD: the side of bytes 0-2 of the clock message (Black's) | 06310's games: a `6x` follows each of Black's moves |
| `70`-`79`, minutes, seconds | the same for the side of bytes 3-5 (White's) | the last `71 32 12` in 06310's memory is bytes 3-5 of its clock answer |
| `6A` | switched on | followed by a scan of every piece on 06310 |
| `6F`, `7B` | a starting position stood; a start-of-game mark | where games begin in both memories |
| `7C` | the board restarted itself | written on 2026-10-12, see below |
| `6B`-`6E`, `7A`, `7D`-`7F`, `00` | other marks | skipped |
| below `40`, where an event would begin | firmware 4.0 only: one to four bytes between events | skipped; time stamps by the look of them (`02` between a lift and the put-down, larger between moves) |

06310's memory holds four games' worth of moves with clock times - `40 34
51 24 71 30 58` is e2 emptied, a white pawn on e4, White's clock at 1:30:58.
That a move made NOW comes out of the next "what changed?" is what the
format and DGT's text both say. It was not seen: nobody moved a piece.

## How fast

At 9600 baud a byte takes a millisecond; the USB adapter hands bytes over
every 16 ms, and that is what a poll costs:

| Question | Answer | There and back (median / worst of the run) |
|---|---|---|
| what changed? - nothing | 6 bytes | **16 ms** / 64 ms (300 polls, 08) |
| version | 8 bytes | 16 ms |
| clock | 13 bytes | 31 ms / 63 ms |
| whole board | 70 bytes | 80 ms / 96 ms |

The real driver on the real loop (19, 64 seconds): **3553 questions, none
unanswered**, 16 ms median from question to whole answer, and each of the
two boards asked what changed **every 32 ms** (median; 272 ms at worst,
when both dumps, both clocks and the look for new boards fall together).
Through the site for four minutes (16, 17): 3475 polls a board, one
position each, never disconnected - and one poll missed by each in the
first second. Those two recordings were made with a 1 ms timer between an
answer and the next question, which is 16 ms on Windows, and with the look
for new boards as the first thing on the line, on top of the boards' first
answers. Both went (14 against 19 is the timer). The site's last run of the
day, three minutes: **4754 polls a board, none missed**, a board asked
every 32 ms.

What that makes of a full loop, counted from those numbers and not
measured: a board is asked what changed once per round of 16 ms a board,
and the whole-board and clock questions take their share on top (they are
asked less often as the loop grows, so that the share stays near 30%).

| Boards | A board is asked what changed every |
|---|---|
| 2 | 32 ms (measured) |
| 6 | about 100 ms; 140 ms with the other questions spread in |
| 12 | about 190 ms; 270 ms with the other questions spread in |

Two things from the first timing run (07) that did not come back: an answer
of 06310 that arrived whole after 5.7 seconds, and another 0.7 seconds into
a dump. Several reads carry the same time stamp on the far side of each
gap, which says the reading program stood still, not the board; more than
ten thousand polls since had no gap. Recorded, not explained.

## What went wrong in the session

- **A question asked too soon** (02): 12799's first "what changed?" is 1319
  bytes, 1.4 seconds, and the script waited 0.6. The next question went out
  on top of it. Both answers are in the recording, cut into each other.
- **A single-board command into a bus answer, and a board that restarted
  itself.** To hear the newer board's serial number alone, recording 11
  sent `45` (serial number, a query) while that board was sending its
  memory on the bus, hoping the old board would answer at once and the new
  one afterwards. It did not answer afterwards - and **its memory has an
  entry since that was not there before: `7C`, "restarted by the
  watchdog"**, five bytes with its time stamp (12 against 06). The board
  answered everything normally a second later and for the rest of the day.
  Nothing else was written to either board. It is the reason the drivers
  now send no single-board command on a line where more than one board
  answered the ping.
- The serial number of the newer board was therefore not read. What the
  collisions show: a serial-number answer came through once as `34 30 37
  33 30` (04) and once with only its tail whole, `37 33 30` (11); the long
  serial number twice as `30 30 30 30 30 34 30 37 33 30` with bit 7 set on
  some bytes (04).

## How the boards were left

"End bus mode" (`88 00 00 08`) was the last thing sent, each time. Both
boards answer single-board commands whatever the mode, so LiveChess and
the single-board driver find them as they were; 06310 will swallow the
first bus command of whoever speaks bus to it next, as it does after any
single-board use. The newer board's memory has the one extra entry
described above. No clock was touched, nothing was set, no piece was moved.

## Still open, and how to close it

1. **A move, live.** With both boards on COM5 and no other program on the
   port: `mix alnasl.loop --port COM5 --watch --seconds 90`, and during it
   play 1. e4 e5 on one board and move any piece on the other. Wanted: a
   `position` line within a blink of each piece put down, and `tx 83 ...`
   / `rx 85 ...` lines carrying the squares. If the positions come only
   every three seconds, "what changed?" does not report live on that board
   and the whole-board question is doing the work - correct, and slow.
2. **A clock on a loop.** The same command with a DGT clock on one board:
   start it, press the lever a few times. Wanted: `clock` lines with the
   times the display shows, White's on the side nearest rank 1.
3. **The newer board's serial number and why it answers as 12799.** Read
   the label under it. Then plug it in ALONE and add its port: the Boards
   page shows its serial number, and the row keeps "answers as 12799"
   from then on, which is how the box knows it on a loop.
4. **Two boards with the same address.** If every board with firmware 4
   answers as 12799, two of them on one loop cannot be told apart. One more
   such board on the loop answers it: `mix alnasl.loop --port COM5
   --discover` should list three.
5. **More than two boards**, and how many rounds the discovery needs when
   answers collide.
6. "Repeat changes" after a non-empty answer; 0x8D.

## What changed in the code

- `Alnasl.Dgt.Bus`: the frames as found; the memory format (`changes/1`);
  a reader that takes up an answer that begins inside a damaged one;
  `serial/2` - the address is the serial number for firmware 1.x only.
- `Alnasl.Dgt.Loop`: who is on a line.
- `Alnasl.Driver.DgtBus`: one question at a time; "what changed?" as the
  usual question, the whole board every few seconds and after every missed
  answer; the clock as its own question, asked at once when a lever is
  written down; a first answer to "what changed?" thrown away; a board
  that is away asked every two seconds; new boards looked for every ten
  seconds without stopping the reading; the port let go of when the last
  board is removed.
- `Alnasl.Driver.DgtSerial`: asks who is on the line before anything else,
  and reads nothing when it is more than one board.
- `Alnasl.Loops`, the Boards page, Help: a port is added, and each board on
  it gets a row. No address is typed anywhere.
- `Alnasl.Dgt.Emulator` behaves as the two boards did, the swallowed first
  command and the collision of single-board answers included.
